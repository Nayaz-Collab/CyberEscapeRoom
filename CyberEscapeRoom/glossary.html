FIELD MANUAL

Background on every concept used in this escape room, with links if you want to go deeper. This isn't required reading to play — just here if you're curious.

Room 1

Caesar Cipher

One of the oldest known encryption methods: every letter in the message is shifted a fixed number of places through the alphabet (e.g. shift 3: A→D, B→E). Because there are only 25 possible shifts, it offers no real security today — but it's a good first step for understanding how substitution ciphers work.

Further reading: Caesar cipher — Wikipedia ↗

ROT13

A special case of the Caesar cipher that always shifts by exactly 13 letters. Because the alphabet has 26 letters, applying ROT13 twice returns the original text — it's used more for obscuring spoilers online than for real security.

Further reading: ROT13 — Wikipedia ↗
Room 2

Phishing

A social-engineering attack where someone impersonates a trusted sender (a bank, a coworker, a well-known company) to trick you into clicking a malicious link, entering credentials, or sending money. It relies on urgency, authority, and familiarity rather than technical exploits.

Further reading: Phishing guidance — CISA.gov ↗

Spoofed sender domains

Attackers often register a domain that looks almost identical to a real one (swapping a letter for a lookalike character, adding a hyphen, or using a different top-level domain) so the "From" address passes a quick glance.

Further reading: Email spoofing — Wikipedia ↗
Room 3

Password strength

Strength isn't just about complexity rules — length matters more than most people expect, and predictable patterns (a common word plus a few digits) stay weak even with a capital letter thrown in. Modern guidance favors long, unique passphrases over short, "complex-looking" passwords.

Further reading: NIST Digital Identity Guidelines (SP 800-63B) ↗

Default / common credentials

Many breaches start with an attacker simply trying well-known default or common passwords (like "Admin123" or "password1") against a login form — no sophisticated hacking required.

Further reading: Pwned Passwords lookup — Have I Been Pwned ↗
Room 4

SQL Injection

Happens when user input is pasted directly into a database query instead of being treated as pure data. A malicious input like ' OR '1'='1 can change the meaning of the query entirely, letting an attacker bypass a login or extract data they shouldn't see.

Further reading: SQL Injection — OWASP ↗

Prepared statements / parameterized queries

The standard fix: the query structure and the user-supplied values are sent to the database separately, so input can never be interpreted as part of the SQL command itself.

Further reading: SQL Injection Prevention Cheat Sheet — OWASP ↗
Room 5

Brute-force / credential attacks

An attacker repeatedly guesses passwords for a given account until one works. In server logs, this usually shows up as a burst of failed login attempts (401 responses) from the same IP address in a short window.

Further reading: Brute Force Attack — OWASP ↗

Log analysis

Security teams review server/access logs to reconstruct what happened during an incident: which IP was involved, how many attempts were made, and exactly when the activity started — the same three things Room 5 asks you to find.

Further reading: Log analysis — Wikipedia ↗
Room 6

Typosquatting

Registering a domain that's a slight misspelling or visual lookalike of a real one (like a zero instead of the letter "o") to catch people who don't look closely, or who mistype a URL.

Further reading: Typosquatting — Wikipedia ↗

Homograph / lookalike-character attacks

A more subtle version of typosquatting that swaps letters for visually identical characters (a capital "I" for a lowercase "l", or letters from another alphabet) so the fake domain is almost indistinguishable at a glance.

Further reading: IDN homograph attack — Wikipedia ↗
